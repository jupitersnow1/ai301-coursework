# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-matches-plan | Every file and hunk in the diff, read against the plan's Files list, change description, Not-in-scope lines, and its Deviations / known-limit notes; then every deliverable the plan names, looked for in the diff. See evidence guide: Plan fidelity. | Both directions hold. (a) Nothing more: every hunk is a change the plan or its deviation notes names (its file or folder, and what it does), a test for that change, or an artifact the repo's stated asks require for this kind of change (a changelog or release-notes entry). Fails on any hunk the plan does not cover: a refactor, rename pass, or rewrite of code the fix does not need; a new option, flag, setting, or config field; a behavior change in another path; a dependency or version bump; or anything the plan's Not-in-scope lines exclude. Commit messages that name extra work ("refactor", "add ... option") count as pointers to such a hunk. (b) Nothing less: every deliverable the plan names (each code change, each named test, each docs change) is in the diff, unless the plan's deviation or known-limit notes record leaving it out. An honestly recorded shortfall passes; a missing deliverable nobody recorded fails. | required |
| description-true | Every factual claim in the PR title and description, including any ticked checklist box, read against the diff, the commit list, and the test evidence. See evidence guide: Plan fidelity. | Every claim about what the PR contains or did is true of the diff and the evidence: a file, test, changelog, or docs change the description says was added is in the diff; a ticked box has its proof in the diff or the evidence; a fidelity claim ("implements the plan exactly", "in full", "no other changes", "no changes beyond it", "no functional changes outside X") holds, meaning the diff has no hunk outside the plan and is not missing a planned deliverable. A claim that something was NOT added (for example "no options added") passes if nothing in the diff adds it. Any one false or contradicted claim fails. A deviation or shortfall the description states openly is a true claim and passes. | required |
| evidence-decisive | The test evidence, read against the plan's test plan and the repro evidence it built on. See evidence guide: Test evidence. | (a) Every failing case the plan's test plan says it will re-run (each repro command, each named failure mode, not the controls) is shown re-run on the changed code, as the command or concrete step that triggers the reported bug, with a specific observable result on it: printed output, an exit code, a value, a count, or an exact message, either pasted or stated as a specific value right next to the command (`# after: ESC[?997;1n (dark)` counts). "Works now", "fixed", "colors work", "verified on my machine", "matches expected", or a run that only exercises the control or an unchanged path (a different input, a single-file case when the bug needs two files, a GET when the bug is a POST) does not count. A plan case left out passes only if the plan's deviation notes or the description say it was left out and why. (b) The repo's own test command (or the suite the plan names) is shown run by name with a result; a failing or skipped check reported with its reason counts. "All tests pass" with no command named fails (b). If neither the repo's stated asks nor the plan name a test command or suite, (b) passes. | required |
| diff-clean | Every added and removed line in the diff, and the commit messages. See evidence guide: Diff quality. | The diff contains only the change and its tests and required artifacts. Fails on any of: a debug print or log line left in (`print`, `eprintln!`, `console.log`, "DEBUG"), commented-out code (old attempts, debug lines, "keeping for reference"), a dead or unused function or `allow(dead_code)` helper added, a new TODO or FIXME, whitespace-only, re-indent, import-reordering, or identical-line remove-and-re-add hunks on code the fix does not change, or a stray file (scratch notes, `plan.md`, `pr_draft.md`, `test_evidence.md`, `comment.md`, build output). Explanatory comments that say why the new code does what it does pass. | required |
| repo-standards | The repo-facts block's PR-template asks and contribution policy (live: `.github/PULL_REQUEST_TEMPLATE.md`, `docs/CONTRIBUTING.md`, and `scope.md`'s house rules), read against the PR title, description, and diff. Treat every package as AI-assisted work. See evidence guide: Standards and comms. | Three halves, all must hold. (a) Template: if the repo has a PR template or a required checklist, every section and checklist item it asks for is present with real content (a checklist item may be answered "n/a" with a reason, and an unticked box is an honest answer, not a gap); an artifact the template requires for this kind of change (a whatsnew or changelog entry "when fixing a bug") is in the diff. With no template, (a) passes. (b) Issue link: if the template or policy asks for a closing line ("closes #", "fixes #") the description has it with the right number; otherwise any reference to the issue number passes, and a description that never names the issue fails only when the repo's stated asks require referencing it. (c) AI disclosure: if the stated policy requires disclosing AI use in pull requests or "in any form", the description discloses it, naming the tool or that AI was used and the extent. A policy that only asks that comments be in the author's own words passes when the text reads as the author's. No AI policy passes (c), except in live mode on Path Review, where the course requires the disclosure in Notes for Reviewers. Requirements that live outside the PR text (CLA signing, CI status, vouching) are not graded here. | required |
| commits-readable | The commit list, read against the repo's stated commit convention, if any. | Each commit message says what the commit changes ("wip", "fix", "misc cleanups" do not), and follows the repo's stated convention where it has one. | preferred |

## Verdict rule

Accept if all five required checks (diff-matches-plan,
description-true, evidence-decisive, diff-clean, repo-standards)
pass. Any required check graded `fail` or `unclear` rejects the
package: `unclear` counts as fail, because a claim nobody can verify
from the package is not ready to submit. The preferred check
(commits-readable) never changes the verdict. The deciding check for
a reject is the first failing required check in table order.

A shortfall the plan's notes and the description both state openly
is not a failure of any check: "less than everything, said plainly"
can be ready. What holds a PR is a gap or an extra that the plan
does not record, or that the description hides or contradicts.
