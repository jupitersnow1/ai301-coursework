# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause (its Diagnosis or Cause line, and any cause the plan comment asserts), read against every step AND every control run in the repro-evidence block, and its Expected/Actual lines. See evidence guide: Diagnosis and grounding. | The stated cause is consistent with every result the repro evidence shows, including each control run. Fails if any repro step or control rules the cause out: the component the plan blames is shown working correctly in a control (it handles the same input fine without the trigger, the feature is shown present and active, the value is shown already wrong before the blamed code runs), or the evidence shows the cost or failure happening with the blamed part out of the loop. A cause adopted from the thread fails the same way if the repro contradicts it. A cause that goes beyond what the repro directly shows still passes if it explains every step and control and nothing in the package contradicts it. | required |
| scope-bounded | The plan's change list, scope / not-in-scope lines, and files or areas, read against the behavior the issue reports and the repro reproduces. See evidence guide: Scope. | The plan makes one bounded change aimed at the reproduced behavior's cause: everything it will build is needed to fix that behavior, plus regression tests for it. Fails if the plan bundles work the issue did not ask for (a refactor or rewrite, a module restructure, a dependency migration or version upgrade, a new user-facing option or setting, a redesign of a neighbouring feature, a new CI matrix, "while I'm in the area" fixes), even when the core fix inside it is right. Also fails if the plan only documents a workaround and leaves the reproduced behavior unfixed. Stated deferrals ("not in scope: X, because Y") and scoping down to part of the issue with reasons pass. Auditing nearby code and reporting findings without fixing them passes. | required |
| executable | The plan's files / areas, approach or change steps, read as instructions a stranger would follow. See evidence guide: Executability. | A stranger could start building today without asking the author anything: the plan names where the change goes (a file, function, module, or code path) and commits to one approach for what the change does. An exact function or line inside a named area may be left as a stated unknown to pin during the build. Fails if the plan's steps are investigation instead of a change ("profile", "look into", "figure out what changed", "fix it once the cause is clear"), if the location is "somewhere" or an unnamed layer ("gocui? tcell? not sure"), or if a real decision is deferred to build time ("upstream or vendored, whichever is easier", "maybe also"). | required |
| test-decisive | The plan's test plan, read against the repro evidence's steps, controls, and Actual line. See evidence guide: Test plan. | The test plan names an observable outcome that would come out differently if the fix did not work: it re-runs the repro (or a test built from it) and states the specific result expected (an exit code, printed output, a value, a position, a count over N runs, a log line). Fails if the only success criterion is subjective ("should feel fast", "should work correctly", "nothing else should feel broken"), is only "run the existing test suite and nothing regresses", or says nothing about the reproduced behavior. | required |
| thread-and-policy | The plan comment, read against (a) the thread highlights from anyone with an OWNER, MEMBER, COLLABORATOR, or CONTRIBUTOR role, and (b) the repo-facts block's contribution policy. Treat every package as AI-assisted work. See evidence guide: Comms. | Both halves hold. (a) If a maintainer-role comment gives explicit direction (identifies the culprit or fix site, proposes or rejects an approach, posts a patch or test build, asks for testing, or says it works as intended), the plan comment engages it: it follows the direction and says so, or names the direction and gives a reason for going another way. Silence about such direction fails. With no maintainer direction in the thread, (a) passes. (b) If the policy requires disclosing AI use in comments or "in any form", the comment discloses it, naming the tool or that AI was used and the extent. A policy with no disclosure requirement for issue comments (no AI policy, AI welcome, "understand your work", human-written comments, or disclosure only in pull requests) passes (b); a human-written-comments rule passes when the comment reads as the author's own words. | required |
| unknowns-named | The plan's risk / unknowns lines and the plan comment's certainty language, read against what the repro evidence shows. See evidence guide: Honesty. | The plan names at least one risk or open question, or says none were found, and does not state as settled anything the package leaves open. | preferred |

## Verdict rule

Accept if all five required checks (diagnosis-grounded,
scope-bounded, executable, test-decisive, thread-and-policy) pass.
Any required check graded `fail` or `unclear` rejects the package:
`unclear` counts as fail, because a plan nobody can verify from the
package is not ready to build from. The preferred check
(unknowns-named) never changes the verdict. The deciding check for a
reject is the first failing required check in table order.
